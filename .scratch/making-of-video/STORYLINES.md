# Storylines v2: 인스타 자동 포스팅 제작기 (발표용)

v1(60초 쇼츠형, 내레이션 없음, 축약 자막)은 목적을 잘못 잡았다. 이 영상은 조회수용이 아니라 **발표용**이다. v1 안(A/B/C)은 git 기록에 남아 있다.

## 이번에 정해진 것

- **보는 사람**: 사용자와 비슷한 수준의 주니어 개발자와 개발자 교육생. 발표장 화면으로 본다.
- **형식**: 가로 16:9, 1920×1080, 30fps. 날짜와 기간은 넣지 않는다.
- **목소리**: Edge TTS 한국어 내레이션(`ko-KR-SunHiNeural` 여성, `ko-KR-InJoonNeural` 남성, `ko-KR-HyunsuMultilingualNeural` 남성 중 하나). 해요체로 쓴다.
- **자막**: 쇼츠식 의미 축약 자막은 쓰지 않는다. 화면 아래에는 내레이션을 그대로 옮긴 말자막을 둔다(레퍼런스와 같은 방식). 말자막을 아예 뺄지는 사용자가 정한다.
- **소재**: devlog S01~S16과 captures의 실제 값만 쓴다. 실제 코드, 실제 테스트 출력, 실제 에러 원문을 보여 준다.

## 레퍼런스에서 가져올 것

레퍼런스: 단테, "임베딩과 RAG, 13분 만에 이해하기". 약 13분, 챕터 16개, 내레이션 약 6,800자(분당 약 520자).

- **도입 질문**: 처음 20초는 보는 사람이 겪어 본 상황 두 개와 질문 하나로 시작한다. 그다음 "오늘은 세 단계로 가요"라며 목차를 보여 준다.
- **홈 무대**: 짙은 바탕 위 패널 하나. 왼쪽 위에 큰 제목, 그 옆에 작은 섹션 라벨(지금 어디인지)이 있다.
- **직접 돌려 보기**: 개념을 설명한 다음 "이제 진짜로 재 볼게요" 하고 실제 터미널 실행 화면을 패널 가득 띄운다. 핵심 줄은 강조한다.
- **틀리는 순간**: 잘 되는 것만 보여 주지 않는다. 실제로 틀린 결과를 보여 주고 왜 틀렸는지 따라간다.
- **정리와 오늘 나온 말**: 끝에서 한 문단으로 요약하고, 용어 카드를 하나씩 다시 짚는다.
- 색, 폰트, 캐릭터는 베끼지 않는다.

Edge TTS 속도(문장 60자에 약 8.6초)도 레퍼런스와 비슷하다. 그래서 길이는 대략 **내레이션 글자 수 ÷ 450~520**분이다.

## A. 글 한 건이 올라가기까지: TDD로 따라가는 제작기 — 추천

*추천 이유: 레퍼런스의 강의 구조를 그대로 쓰면서, 처음부터 끝까지 따라갈 실제 예시가 하나 있기 때문이다. "첫 번째 글 한 건"이 그 예시다. 교육생이 따라 하기 가장 쉽다.*

**질문**: "글 하나를 정해진 시간에 인스타에 자동으로 올리려면, 무엇이 필요할까요?"

**도입**:
- 상황 두 개로 연다. 하나는 "매일 저녁 8시에 글을 올리기로 했는데 깜빡한다", 다른 하나는 "인스타는 글만 올릴 수 없다"(S01)이다.
- 그다음 목차를 세 단계로 보여 준다.
  1. 테스트로 설계하기
  2. 진짜 서버와 만나기
  3. 혼자 돌게 하기

**흐름** (챕터마다 개념 설명 → 실제 터미널 → 한 줄 짚기 → 교훈):
1. **빈 저장소**: `fatal: 현재 'main' 브랜치에 아직 아무 커밋도 없습니다`. 요구사항을 정하고 Python과 TDD를 고른 이유를 말한다. (S01)
2. **첫 빨간불**: 아직 없는 코드를 부르는 테스트를 쓴다. `ModuleNotFoundError` → `1 passed`. 가짜 게시기는 왜 쓰는지 설명한다. (S02)
3. **같은 글이 두 번**: 크론은 같은 큐를 다시 본다. `assert 2 == 1`. 멱등성을 설명한다. (S03)
4. **실패를 반복하면 스팸**: 실패한 글은 다시 보내지 않는다. 가짜도 읽혀야 한다는 점도 짚는다. (S04, S05)
5. **보내기 전에 거절하기**: 2200자, 해시태그 30개 같은 플랫폼 제한을 검증 규칙으로 만든다. (S06)
6. **20시는 어느 나라의 20시?**: `TypeError: can't compare offset-naive and offset-aware datetimes`. 글 하나 때문에 큐 전체가 멈췄다. (S07)
7. **인스타는 바로 올리지 않는다**: 컨테이너 → 상태 확인 → 게시의 3단계를 그림으로 보여 준다. `IN_PROGRESS`를 기다리는 테스트 `1 == 3`. (S08)
8. **영원히 기다리는 코드**: `IndexError: pop from empty list`. 가짜 서버였으니 멈췄지, 진짜 서버였다면 영원히 돌았다. 타임아웃을 넣는다. (S09)
9. **첫 실제 응답은 거절**: `code 190`. 그래도 요청은 Meta까지 갔다. (S10)
10. **코드 밖의 벽**: 개인 계정은 API를 못 쓴다. 문서에 나온 메뉴가 없다(Unified Login). 주소와 버전을 설정으로 빼 둔 덕분에 두 줄만 고쳤다. (S11, S12)
11. **같은 서버가 이번엔 대답했다**: `quota_usage 0 / 100`. (S13)
12. **첫 게시**: 코드는 한 줄도 고치지 않았는데 한 번에 올라갔다. `first-post: posted`, 실제 게시물 화면. (S14)
13. **혼자 돌게 하기**: gitleaks로 토큰을 막는다(짧게). GitHub Actions에서 15분마다 돌린다. 두 실행이 겹치면 S03이 다시 나타난다. 조용한 실패 대신 시끄러운 실패를 고른다. (S15, S16)
14. **정리와 오늘 나온 말**: TDD, 가짜 객체, 멱등성, 시간대(naive와 aware), 폴링과 타임아웃, 토큰, 프로페셔널 계정, 크론, 동시 실행 막기.

**룩**:
- 짙은 먹색 바탕(`#1F2421` 근처)에 둥근 패널 하나를 둔다. 왼쪽 위에 제목 "인스타 자동 포스팅", 옆에 챕터 라벨을 둔다.
- 오른쪽 위에는 세 단계 진행 지도를 두고, 지금 단계를 표시한다.
- 터미널 화면은 실제 출력이다. 빨강은 실패, 초록은 통과에만 쓴다.
- 첫 번째 글 카드(노트북 사진)는 장면이 바뀌어도 같은 물건으로 반복해서 나온다.

**예상 길이**: 약 10~12분.

## B. 버그 아홉 개의 해부: 증상 → 원인 → 테스트 → 수정

**장치**: 결과부터 보여 준다. 실제 게시물로 시작해서 "이게 한 번에 올라간 건, 그 전에 아홉 번 틀렸기 때문이에요"라고 말한다. 그다음 버그를 하나씩 해부한다.

**형식**: 챕터마다 모양이 같다. 증상(실제 에러 원문) → 원인(코드 몇 줄) → 그 버그를 잡는 테스트 → 고친 코드 → 한 문장 교훈. 반복되는 형식이라 교육생이 노트하기 쉽다. 이야기 흐름은 A보다 약하다.

**다루는 버그**:
- 같은 글 두 번 게시
- 실패 반복
- 시간대
- 기다림 무한 루프
- `code 190`
- 개인 계정
- 메뉴 변경
- 동시 실행
- 조용한 실패

**룩**: 패널을 반으로 나눠 왼쪽에 에러, 오른쪽에 코드를 둔다. 고친 줄은 diff처럼 초록 배경으로 칠한다.

**예상 길이**: 약 8~10분.

## C. 교과서에 없는 것들: 코드 밖에서 막힌 순간들

**장치**: "코드는 다 됐는데, 안 올라가요"로 시작한다. TDD 부분(S02~S09)은 2분 안쪽으로 빠르게 지나간다. 나머지 시간은 학원에서 잘 안 가르치는 것들에 쓴다.
- 플랫폼 규칙: 계정 종류, 하루 100개 한도, 이미지는 URL로만 받음
- 바뀌는 문서: Unified Login
- 토큰과 비밀 정보: `code 190`, gitleaks
- 서버에서 돌리기: Actions, 동시 실행
- 실패를 알리는 방법

**형식**: 벽을 하나씩 만나고, 넘는 방법을 보여 준다.

**룩**: 실제 화면 캡처(Meta 앱 화면, GitHub Actions 실행 화면, 인스타 게시물)를 많이 쓰고, 터미널은 적게 쓴다.

**예상 길이**: 약 7~9분.
